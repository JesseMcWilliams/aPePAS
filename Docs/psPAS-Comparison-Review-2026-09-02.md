# aPePAS vs. psPAS: Reference Review

**Scope:** Authentication, Accounts, Applications, Safes/SafeMembers, Platforms, and a lighter pass over Groups/Users/Reports/Custom. aPePAS (`C:\Code\aPePAS`) was reviewed against psPAS 8.0.20 (`C:\Code\References\pspas.8.0.20`), the mature open-source PowerShell module for the same CyberArk PAS/ISPSS API, to surface gaps, bugs, and patterns worth adopting.
**Date:** 2026-09-02

## The one finding that matters most

Every area of this review turned up the same root issue independently, which is the strongest signal in the whole review: **aPePAS's shared HTTP engine passes request bodies to `Invoke-WebRequest` as plain strings, where psPAS deliberately converts them to raw UTF8 byte arrays first.**

In `Modules\CyberArkComms.psm1`, `Invoke-CyberArkAPI` builds `$bodyString` via `ConvertTo-Json` and assigns it directly to `$iwrParams['Body']` (around line 374) before calling `Invoke-WebRequest @iwrParams`. psPAS's `Private\Invoke-PASRestMethod.ps1` (lines 257–263) does the same JSON build but then explicitly does `$PSBoundParameters['Body'] = [System.Text.Encoding]::UTF8.GetBytes($Body)`, with a comment stating this is done specifically so PowerShell's own ParameterBinding/module logging records the type name `System.Byte[]` instead of the literal request content. `New-PASSession.ps1` applies the identical conversion to its own logon bodies for the same reason. aPePAS's `CyberArk.Auth.SelfHosted.psm1` (`Invoke-PVWALogon`) has the same gap on the CyberArk/LDAP/RADIUS/PKI logon calls, and `CyberArk.Auth.ISPSS.psm1` has it on the OAuth2 client-credentials and challenge-response calls.

This matters because if the target environment has PowerShell Module Logging or Script Block Logging enabled by Group Policy — a realistic, common setting on a host running a privileged-access tool — the plaintext JSON body for every write call gets recorded in the Windows PowerShell Operational event log, independent of anything aPePAS's own log masking does. And aPePAS's own masking is good: `CyberArkLogging.psm1`'s `$script:SensitivePatterns` already has a regex specifically aimed at JSON-quoted `password`/`secret`/`token`/`credential` keys, with a comment naming `CyberArkComms`'s DEBUG/-FileOnly body logging as the reason it's there. That protects the app's own log file. It does nothing for the OS-level logging path psPAS is guarding against. Concretely, this touches: `Add-PASAccount`/`Invoke-AccountsAdd` and `Invoke-AccountsChangeInVault` (plaintext account passwords), `Invoke-PASCPMOperation`/`Invoke-AccountsChangeImmediate` (`NewCredentials`), self-hosted CyberArk/LDAP/RADIUS logon (the vault password itself), ISPSS `ClientCredentials` (OAuth client secret), `Invoke-SafeMembersAdd`/`Update` (full permission bodies — lower sensitivity but still worth covering for consistency), and `Invoke-ApplicationsAddAuthMethod` (`AuthValue` — also missing from the log-masking pattern list, so it's exposed in the app's *own* debug log too, not just OS logging).

The fix is small and mechanical: wherever a string body is about to be handed to `Invoke-WebRequest`/`Invoke-RestMethod`, encode it first — `[System.Text.Encoding]::UTF8.GetBytes($bodyString)` — the same one-line pattern psPAS uses in both of its call sites. Worth doing centrally in `Invoke-CyberArkAPI` (covers every API module in one place) and separately in the three raw `Invoke-RestMethod` call sites inside the Auth modules, since those bypass the Comms layer entirely.

## Authentication

aPePAS's Auth layer is architecturally more mature than psPAS's in several respects — it's not a case of psPAS simply being ahead. Splitting `CyberArk.Auth.Common/ISPSS/SelfHosted.psm1` into focused modules (per `Docs\Auth-Module-Rework-Design.md`) avoids the single 900-line parameter-set maze that is psPAS's `New-PASSession.ps1`; DPAPI-backed profile persistence (`Save-AuthToken`/`Import-AuthToken`), a WebView2-based interactive/SSO/SAML/OIDC flow, and the planned proactive-refresh and 401-vs-403 handling are all things psPAS doesn't attempt. That said, three things stood out worth pulling from or reconciling against psPAS.

The plaintext-body issue above is the most important one here specifically because it hits every self-hosted password logon and every ISPSS client-credentials exchange — the two paths where the secret in the body *is* the credential itself, not just account metadata.

Second, `Resolve-IdentityTenantURL` in `CyberArk.Auth.ISPSS.psm1` discovers the Identity tenant by probing three guessed candidate hostnames (`{subdomain}.cyberark.cloud`, `{subdomain}-userportal.cyberark.cloud`, `{subdomain}.privilegecloud.cyberark.cloud`) with `HttpWebRequest` and inspecting redirects, falling back to a constructed guess if nothing matches. psPAS's `Private\Find-SharedServicesURL.ps1` instead calls CyberArk's own documented platform-discovery endpoint (`https://platform-discovery.cyberark.cloud/api/v2/services/subdomain/{subdomain}`), which returns the identity, pcloud, and every other shared-service URL directly as structured JSON — no guessing, no redirect-chasing, and it's the same endpoint `New-PASSession`'s `ISPSS-Subdomain-*` parameter sets use. Switching to that endpoint would be both simpler and more reliable than the current probe-and-fallback approach, and would also remove the three-candidate list as a maintenance burden if CyberArk ever changes redirect behavior.

Third, `CyberArk.Auth.SelfHosted.psm1` hardcodes `PVWA_SESSION_EXPIRY_MIN = 20` as the assumed PVWA idle-session lifetime for every self-hosted auth method. That's PVWA's common default, but it's an admin-configurable value. psPAS instead calls `Get-PASSessionTimeout` (`GET /api/Settings/Timeout`) right after logon to read the server's actual configured value, and then tracks elapsed idle time against it (`Get-PASIdleTimeRemaining`) to warn the caller before a request would trip the timeout. aPePAS's fixed 20-minute assumption means a token could be treated as still valid past an environment's real (shorter) timeout, or discarded early in an environment configured longer. Also worth a look: aPePAS's self-hosted password/Shared/PKI/PKIPN methods never call the PVWA logoff endpoint (psPAS's `Close-PASSession` posts to `/API/Auth/Logoff`) — there's no explicit session invalidation on completion, which for methods that hold a concurrent-session slot server-side means the slot stays occupied until natural timeout rather than being released immediately.

## Accounts

Coverage of the core account-lifecycle operations (add, get, list, update, delete, unlock, change/reconcile/verify via CPM, link/unlink, resume management, get credential) is solid and maps cleanly to psPAS's equivalents. Two endpoint-path items are worth a live check rather than a code fix: `Invoke-AccountsCancelCpmTask.ps1` calls `POST /API/Accounts/{id}/StopImmediateAutoMgmtOperations`, where psPAS's `Stop-PASCPMTask.ps1` calls `POST /API/Accounts/{id}/Cancel/` — these are two different-looking endpoints for what should be the same operation, and given every sibling CPM-operation endpoint (`/Change`, `/Reconcile`) matches psPAS exactly, this one divergence is worth confirming against a live tenant rather than assuming either side is wrong from reading code alone. Similarly, `Invoke-AccountsResumeAutoManagement.ps1` uses a JSON-Patch `PATCH /API/Accounts/{id}/` where psPAS's `Resume-PASCPMAutoManagement.ps1` uses a dedicated `POST /API/Accounts/{id}/Resume/` — likely equivalent, but two paths for one intent is worth reconciling.

One structural fragility in the shared engine: `Invoke-CyberArkAPI`'s pagination only recognizes a fixed allowlist of response-collection property names (`value`, `Safes`, `Members`, `Accounts`, `Users`, `Platforms`, `Groups`). psPAS's `Get-NextLink.ps1` instead discovers the collection property dynamically and supports `nextLink`, `nextCursor`, and count-driven paging. For every endpoint used today this is a non-issue since they all return `value`, but it means any future endpoint returning results under a different property name would silently return only its first page with no error. Worth generalizing before it bites.

On the positive side, aPePAS's transparent multi-page merging (callers never have to think about paging) and the "iterate by safe" mode in `Invoke-AccountsList.ps1` — working around CyberArk's roughly 20,000-record search cap by paging per-safe instead of globally — are both genuine improvements psPAS doesn't have; psPAS requires callers to explicitly pipe into `Get-NextLink` themselves. Scope-wise, aPePAS doesn't cover psPAS's Dependent Accounts, Discovered/Discovered-Local Accounts (onboarding), Personal Admin Accounts, Just-In-Time Access, or SSH key retrieval — these are distinct CyberArk feature areas that are plausibly out of scope by design rather than oversights, worth a one-line confirmation rather than treating as gaps.

## Applications

The core Add/Get/List/Delete surface and the auth-method add/list/delete surface are present and functional, but there's a real, structural gap: `Invoke-ApplicationsAddAuthMethod.ps1` supports five auth-method types (path, certificateSN, hash, machineAddress, osUser) via a flat `AuthType`/`AuthValue` pair, while psPAS's `Add-PASApplicationAuthenticationMethod.ps1` has a sixth type, `certificateattr`, with independent `Subject`, `Issuer`, and `SubjectAlternativeName` fields sent as separate JSON properties rather than packed into one value. There's currently no way to configure certificate-attribute-based application authentication in aPePAS at all.

Validation is thinner than psPAS in a few concrete spots on `Invoke-ApplicationsAdd.ps1`: `AccessPermittedFrom`/`AccessPermittedTo` are checked as integers but not range-validated to 0–23 (psPAS: `[ValidateRange(0,23)]`), and the surrounding comments/error text mislabel these as "epoch seconds" when they're actually hour-of-day values per the module's own schema description — worth fixing the label regardless of the validation gap. `AppID`, `Description`, `BusinessOwnerFName`, and `BusinessOwnerPhone` also lack the length/charset checks psPAS applies before ever calling the API, so invalid input currently surfaces as a late, less-clear server error. Separately, `Location` is optional in aPePAS's schema but mandatory in psPAS's — worth a live check to see which is actually correct. And as noted above, `AuthValue` isn't in `CyberArkLogging.psm1`'s masked-pattern list, so a `hash`-type credential value is written unmasked to aPePAS's own debug log even before the OS-logging issue applies.

On the positive side, the CSV boolean-coercion logic (matching a truthy-token whitelist rather than a naive `[bool]` cast, which in PowerShell treats any non-empty string including `"false"` as true) is a correct, deliberate fix for a genuine PowerShell pitfall that psPAS doesn't need to worry about since it isn't CSV-driven.

## Safes and SafeMembers

The safe-member permission model is the part of this area with the most riding on it, and it checks out clean: aPePAS's `Get-PermissionSet`/`Get-SpecifiedPermissions` cover all 22 boolean permission fields psPAS's `Private\ConvertTo-SortedPermission.ps1` defines, with correct camelCase keys and correct mutual exclusivity between the two authorization-level flags. No gap in the permission surface itself.

Two things worth attention below that. First, `Invoke-SafesAdd.ps1`/`Invoke-SafesUpdate.ps1` only check that SafeName is non-empty, where psPAS's `Add-PASSafe`/`Set-PASSafe` validate length (0–28 characters) and reject the character set CyberArk itself disallows (`\ / : * < > " . |`, leading whitespace) before calling the API — the same late-error pattern as the Applications validation gap above, and probably worth fixing the same way. Second, aPePAS's own role-preset names (ReadOnly/EndUser/PowerUser/SafeManager) collide in name but not behavior with psPAS's presets (which mirror CyberArk's own PVWA role names): psPAS's "ReadOnly" grants `retrieveAccounts`, while aPePAS's "ReadOnly" deliberately does not. That's a defensible design choice, but the name collision means an administrator carrying intuition over from PVWA or psPAS could reasonably expect retrieve access from a role called ReadOnly and not get it — worth a documentation callout rather than a code change.

The large `AddFromTemplate`/`AddFromTemplateRole`/`UpdateFromTemplateRole` files (documented in `Docs\Add-Safe-From-Template-Design.md`) are a deliberate custom provisioning feature with no psPAS equivalent, and they hold up on inspection: they reuse the same underlying endpoints and body shapes as the plain Add modules rather than introducing new API surface, and every one of them has a corresponding Pester test. Their size reflects the feature's scope, not sloppiness. Minor gaps worth knowing about: no `Quota` (safe size limit) support in Add/Update, no server-side `sort`/`includeAccounts`/`useCache` on Get/List, and the all-safes mode in `Invoke-SafeMembersList.ps1` does one unfiltered GET per safe with no equivalent to psPAS's `memberType`/`membershipExpired`/`search` server-side filters — functional, just more chatty than it needs to be for a full-tenant member audit.

## Platforms

This is the one area where the gap looks like unfinished work rather than a deliberate boundary. aPePAS currently implements only `Get` and `List` for platforms, while psPAS covers the full lifecycle: enable, disable, copy, rename, import, export, remove, target-settings updates, PSM config, and platform secrets. That would be a reasonable scope choice on its own, except aPePAS's own README lists "platform administration" as a stated feature and describes the same CSV-driven write pattern (Add/Update/Delete) that Safes, SafeMembers, Users, and Groups already implement — so the complete absence of any platform mutation endpoint reads as inconsistent with the project's own stated scope rather than an intentional read-only design for this one area. Master Policy support (`Get`/`Set-PASMasterPolicy`, 16 configurable flags covering dual control, multi-level approval, password rotation cadence, etc.) is similarly absent with no aPePAS equivalent at all.

Read-side filtering is also noticeably shallower: `Invoke-PlatformsList.ps1` supports only `Search` and an `ActiveOnly` flag, where psPAS's `Get-PASPlatform.ps1` additionally filters by `SystemType` and exposes separate views for groups, rotational groups, dependents, and per-target settings scope. Worth noting as a genuine positive: both `Invoke-PlatformsGet.ps1` and `Invoke-PlatformsList.ps1` defensively fall back across multiple possible field-name shapes (`general.id`/`general.PlatformID`/root `id`/root `PlatformID`) with an inline comment documenting a prior bug where this fallback existed on Get but was missing on List — that's a real fix already made, not a live issue.

## Groups, Users, Reports, and Custom scripts

Groups' CRUD surface is close to complete, with two things worth verifying against a live tenant rather than treating as confirmed bugs from code alone: `Invoke-GroupsGetMembers.ps1` does a plain `GET` with no query parameters, while psPAS's `Get-PASGroup.ps1` gates an `includeMembers` flag behind API version 12.0 — if that flag is actually required server-side, `GetMembers` could be silently returning empty member lists on some PVWA versions. And `Invoke-GroupsAddMember.ps1`/`RemoveMember.ps1` default `MemberType` to `'EPVUser'`, where psPAS validates the same field against `('domain','vault')` for the identical endpoint — one of these two value sets is likely stale and worth reconciling against current CyberArk documentation.

Users and Reports are both deliberately read-only in aPePAS (confirmed by the README), and both cover meaningfully less than psPAS's full surface — Users lacks create/update/enable/disable/password-reset, Reports lacks export, scheduling, and license reporting — but that reads as an intentional, stated scope boundary rather than an oversight, unlike Platforms above where the README's own claims contradict the gap. One item worth a quick confirmation: aPePAS restricts Reports to self-hosted only, while psPAS's `Get-PASReport` works against both self-hosted and ISPSS from v14.6 onward — worth checking whether that restriction is deliberate or just unexplored.

The Custom scripts (`ExportAll`, `ExportEntitlements`, `ExportGroupMembersLDAP`, `ExportGroupMembersLocal`, `TestApi`) have no psPAS equivalent since they're aPePAS-specific composite tools, and they're generally solid — the recursive group-expansion scripts guard against cycles with a visited-set rather than recursing unbounded, and `TestApi` masks auth headers before logging. One small robustness gap: `Invoke-CustomExportAll.ps1`'s loop over every List module doesn't check a module result's `IsFatal` flag, so a 401 partway through will keep calling the remaining endpoints instead of stopping early the way `ExportEntitlements` correctly does.

## Suggested priority order

Fix the plaintext-body-to-`Invoke-WebRequest` issue first — it's the one finding that showed up independently in every area, it's a small, mechanical change, and it's the only item here with genuine credential-exposure risk. After that, the Platforms gap (mutation operations and Master Policy) is the next most consequential item since it contradicts the project's own stated scope rather than being a reasonable boundary. Everything else — endpoint-path double-checks (Cancel/Resume CPM operations, Groups member-type values), client-side validation gaps (SafeName, AppID/Applications fields), and the pagination allowlist fragility — is worth cleaning up but isn't urgent, and the scope gaps in Accounts/Users/Reports look like deliberate, defensible design choices rather than defects.
